- **Rate limiting, built as a genuinely atomic Postgres function, not application-code read-then-write** (`check_and_consume_ai_rate_limit` migration): a plain "read the row, check it, write it back" would race under concurrent requests from the same caller (both could read count=N, both write N+1, letting one extra request through right at the cap) -- one `INSERT ... Starting caps: guests 5/min & 20/day, signed-in 10/min & 60/day -- checked *before* the paid Gemini call, since that ordering is the actual cost protection, not a courtesy.

### 2026-09-15 (evening, `chore/AWSsetup`)

- **Lambda/EventBridge automation of the scraper trigger, built as a real guided walkthrough** (three genuinely new AWS concepts for the user, taught one at a time before any of it was built, same teaching-first pattern as the S3 session earlier the same day): Secrets Manager, an IAM role for a third *kind* of identity (not a human, not a CLI credential — a piece of AWS-run code acting via temporary auto-rotated credentials, no permanent access key involved at all), and Lambda + EventBridge Scheduler on top.
- **Secrets Manager**: one secret holding `SUPABASE_SERVICE_ROLE_KEY`, created via the console's "Other type of secret" flow, no rotation (not applicable to this kind of value). Chosen deliberately over a plain Lambda environment variable — env vars are plaintext-visible to anyone who can view the function's config, whereas Secrets Manager requires its own separately-grantable `secretsmanager:GetSecretValue` permission.
- **Real gap caught before deploying, not after**: the existing code (`scraper/supabaseClient.ts`) only ever read `process.env.SUPABASE_SERVICE_ROLE_KEY` directly — no code existed yet to actually fetch anything from Secrets Manager. Talked through two options (real SDK fetch vs. a simpler plain Lambda env var); user chose the real fetch to keep the implementation genuinely production-style, matching the project's stated priorities.
- **Turned out simpler than first scoped**: initially planned as a runtime `if` in `supabaseClient.ts` (branch on whether an AWS-Lambda-only env var is set). Investigating the actual module graph first (per CLAUDE.md's "work through debugging/logic together" rule extended here to design, not just bugs) found `lambdaHandler.ts` is the *only* file `tsconfig.lambda.json` ever bundles, and nothing else imports it — so it's Lambda-only code, always, and the runtime branch wasn't needed at all. Landed on: `lambdaHandler.ts`'s `handler()` unconditionally fetches the secret via `GetSecretValueCommand` (auth implicit via the execution role, zero credentials in code) and sets `process.env.SUPABASE_SERVICE_ROLE_KEY`, then `await import()`s `supabaseClient.ts`/`runScrape.ts` — a dynamic import specifically so module evaluation (and `supabaseClient.ts`'s existing top-of-file env read) happens after the secret lands, not before. Zero changes needed to `supabaseClient.ts` itself or any of the four CLI scripts that also import it (`scrape`/`promote`/`academic-year:create`/`academic-year:activate`) — all still just read `.env.local` exactly as before.
- **Three IAM roles total, least-privilege, each scoped to one job** — same discipline as the S3 IAM users, applied to genuinely different identity types: the Lambda's own execution role (`AWSLambdaBasicExecutionRole` + one inline policy scoped to exactly the one secret's ARN), and the EventBridge Scheduler's auto-generated role (`lambda:InvokeFunction` scoped to exactly the one function's ARN). No VPC — default Lambda networking already reaches the public internet, a VPC would only add a NAT gateway cost for zero benefit here.
- **Deployed and verified for real, not just reviewed**: `npm run build:lambda` (added `@aws-sdk/client-secrets-manager` to both `package.json` and `scraper/lambda-package.json` first), zipped via `Compress-Archive` (PowerShell — `zip` isn't available in this Windows environment), uploaded through the console, handler set to `scraper/lambdaHandler.handler`, timeout bumped 3s → 2min, memory 256MB. A real manual "Test" invoke in the console succeeded end to end — CloudWatch logs showed all six scrape groups (undergrad/grad tuition, housing, resident/block dining, parking) staging cleanly with zero errors, `Billed Duration: 9445 ms`, `Max Memory Used: 149 MB` — comfortable headroom on both budgets. Confirms the full chain worked on a real run: implicit role auth to Secrets Manager, the fetched key's validity against real staging tables, and the dynamic-import ordering trick all correct in practice, not just on paper.
- **EventBridge Scheduler**: `cron(0 6 1 * ? *)` (06:00 UTC, 1st of every month) — landed on monthly as a reasonable default (UMD typically only publishes real rate changes once a year, over the summer; monthly is cheap and mainly catches corrections/revisions faster than a slower cadence would).
- Full details (ARN, exact role/policy names, function config) written up in `docs/BUILD-REFERENCE.md`'s new `## AWS Lambda scraper automation` section — step 12 now reads **Done**. `tsc`/lint/66 tests/`build:lambda` all verified clean after the code change.

- **Academic-year rollover feature (branch `feat/academic-year-rollover`), several rounds of design conversation before any code.** Started from auditing the scraper/staging/promote pipeline against every migration since it was built -- confirmed all 10 scraped rate tables are fully covered column-for-column, but found a real, previously-unnoticed gap: `academic_years.is_current` (added 2026-09-03) was never wired into the pipeline at all, and `getRatesBundle()` always resolving "whichever year is current" meant a saved scenario from a past year would silently resolve to blank/null fields the moment a second year ever went live -- a latent bug, unreachable until now, but real.
